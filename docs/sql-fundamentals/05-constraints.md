# 1.9 Constraints and data integrity

!!! abstract "Chapter card"
    **Stage:** 1 (sections 1 to 5), 2 (sections 6 to 8) · **Prerequisites:** 1.7, 1.8 · **Time:** 2 hours

## 1. Overview

A **constraint** is a rule the database enforces on every row, no matter which
application, script or person writes the data. Application validation protects
one code path; constraints protect the data.

| Constraint | Rule | FreshMart example |
|---|---|---|
| `NOT NULL` | A value is required | `customers.email` |
| `PRIMARY KEY` | Unique and not null; one per table | `pk_orders` |
| `UNIQUE` | No two rows share the value (nulls allowed) | `uq_products_sku` |
| `FOREIGN KEY` | Value must exist in the parent | `fk_orders_customer` |
| `CHECK` | A condition on the row must not be false | `ck_reviews_rating` (1 to 5) |
| `DEFAULT` | Not a constraint, but supplies a value when none is given | `status DEFAULT 'PLACED'` |

## 2. Why

Without `ck_inventory_reserved`, a bug in any one of several services could
reserve more stock than exists, and the error would surface days later as an
order that cannot be shipped. With it, the faulty statement fails immediately,
at the source.

Constraints also inform the **optimizer**: a declared foreign key lets Oracle
remove unnecessary joins, and `NOT NULL` lets it use more index access paths.

## 3. Syntax

Constraints can be written inline with a column or out of line (required for
multi-column rules). Out-of-line and named is the standard in this playbook.

```sql
CREATE TABLE reviews (
    review_id   NUMBER(12) GENERATED BY DEFAULT ON NULL AS IDENTITY,
    product_id  NUMBER(10) NOT NULL,
    customer_id NUMBER(10) NOT NULL,
    rating      NUMBER(1)  NOT NULL,
    CONSTRAINT pk_reviews PRIMARY KEY (review_id),
    CONSTRAINT uq_reviews_product_customer UNIQUE (product_id, customer_id),
    CONSTRAINT fk_reviews_product  FOREIGN KEY (product_id)  REFERENCES products (product_id),
    CONSTRAINT fk_reviews_customer FOREIGN KEY (customer_id) REFERENCES customers (customer_id),
    CONSTRAINT ck_reviews_rating CHECK (rating BETWEEN 1 AND 5)
);
```

## 4. Each constraint in action

```sql
INSERT INTO reviews (product_id, customer_id, rating) VALUES (1, 101, 5);
-- ORA-00001: unique constraint (FRESHMART.UQ_REVIEWS_PRODUCT_CUSTOMER) violated
-- Rahul has already reviewed product 1.

INSERT INTO reviews (product_id, customer_id, rating) VALUES (2, 101, 6);
-- ORA-02290: check constraint (FRESHMART.CK_REVIEWS_RATING) violated

INSERT INTO reviews (product_id, customer_id, rating) VALUES (99, 101, 4);
-- ORA-02291: integrity constraint (FRESHMART.FK_REVIEWS_PRODUCT) violated - parent key not found

INSERT INTO reviews (product_id, customer_id, rating) VALUES (2, 101, NULL);
-- ORA-01400: cannot insert NULL into ("FRESHMART"."REVIEWS"."RATING")
```

The constraint name in the message tells you which rule failed. That is why
constraints are named.

### CHECK and NULL

A check constraint rejects a row only when the condition is **false**. If it
evaluates to *unknown* (because of a null), the row is accepted. Combine `CHECK`
with `NOT NULL` when a value is mandatory.

Check constraints may reference only columns of the same row. They cannot call
`SYSDATE`, query other tables or use sequences.

### Foreign key actions

| Declaration | When the parent row is deleted |
|---|---|
| *(default)* | The delete is refused while children exist (`ORA-02292`) |
| `ON DELETE CASCADE` | The children are deleted too (`cart_items` when a cart is deleted) |
| `ON DELETE SET NULL` | The child's foreign key becomes null |

Oracle has no `ON UPDATE CASCADE`. Primary keys should not change; this is one
more reason to use surrogate keys.

Use `ON DELETE CASCADE` only for true parts of a whole (cart items, address
lines). Never cascade from business entities such as customers to orders.

## 5. How Oracle enforces constraints

- `PRIMARY KEY` and `UNIQUE` are enforced with an **index**. Oracle creates one unless a suitable index already exists.
- `FOREIGN KEY` is checked by looking up the parent key's index on insert and update of the child, and by looking for children on delete of the parent.
- Checks happen at the **end of each statement** by default, not row by row. A statement that swaps two unique values succeeds.

!!! warning "Index your foreign keys"
    Oracle does not create an index on foreign key columns. If the child column
    is unindexed, deleting a parent row (or updating its key) takes a **table
    lock** on the child and full-scans it. This is a classic cause of blocking
    and deadlocks. FreshMart indexes every foreign key
    (`sql/schema/01_tables.sql`).

## 6. Constraint states and deferral :material-school: Stage 2

| State | Checks new changes | Vouches for existing rows |
|---|---|---|
| `ENABLE VALIDATE` (default) | Yes | Yes |
| `ENABLE NOVALIDATE` | Yes | No |
| `DISABLE NOVALIDATE` | No | No |
| `RELY DISABLE NOVALIDATE` | No | Tells the optimizer to trust it (data warehouses) |

```sql
-- Add a constraint to a large, busy table in two short steps
ALTER TABLE orders ADD CONSTRAINT ck_orders_fee CHECK (delivery_fee <= 500) ENABLE NOVALIDATE;
ALTER TABLE orders MODIFY CONSTRAINT ck_orders_fee VALIDATE;   -- does not block DML
```

**Deferrable constraints** are checked at `COMMIT` instead of at the end of the
statement. Use them for circular references or bulk rearrangements.

```sql
ALTER TABLE employees ADD CONSTRAINT fk_employees_manager
    FOREIGN KEY (manager_id) REFERENCES employees (employee_id)
    DEFERRABLE INITIALLY IMMEDIATE;

SET CONSTRAINT fk_employees_manager DEFERRED;   -- for this transaction
-- insert employee and manager in any order
COMMIT;                                         -- checked here; a violation rolls back the whole transaction
```

A deferrable unique or primary key constraint is policed by a **non-unique**
index, which costs the optimizer some access paths. Make a constraint deferrable
only when you need it.

## 7. Cross-row and cross-table rules

Some rules span rows or tables: *"an order's total must equal the sum of its
lines"*, *"a customer may have only one default address"*.

| Tool | Fits | Notes |
|---|---|---|
| Unique function-based index | "At most one X per Y" | See the example below |
| Foreign key to a composite unique key | "Child must match parent's type" | Purely declarative |
| Materialized view with a check constraint | Aggregate rules | Fast refresh on commit; advanced |
| Transactional API (package) | Multi-step rules | The single write path; `order_pkg` |
| Trigger | Last resort | Hard to make correct under concurrency |
| **SQL assertion** | Any multi-row / multi-table condition | :material-tag: **26ai (23.26.1+)** |

```sql
-- At most one default address per customer: only the 'Y' rows enter the index.
CREATE UNIQUE INDEX uq_addresses_one_default
    ON addresses (CASE WHEN is_default = 'Y' THEN customer_id END);
```

### Assertions

The SQL standard has defined `CREATE ASSERTION` since 1992, but mainstream
databases did not implement it. Oracle announced support in the 26ai release
updates (reported for 23.26.1). An assertion is a schema-level boolean
condition that must hold after every transaction:

```sql
-- Illustrative: verify the exact syntax and restrictions in the SQL Language
-- Reference for your release update before using it.
CREATE ASSERTION reserved_not_above_on_hand CHECK (
    NOT EXISTS (SELECT 1 FROM inventory WHERE qty_reserved > qty_on_hand)
);
```

On 19c, 21c and 23ai this statement does not exist; use the techniques in the
table above.

## 8. Production recommendations and mistakes

| DO | DON'T |
|---|---|
| Declare every rule the database can enforce | Rely on "the application checks that" |
| Name all constraints | Accept `SYS_C00...` names |
| Index foreign keys | Leave child tables to be locked on parent deletes |
| Add constraints to big tables with `NOVALIDATE` then `VALIDATE` | Add a validating constraint in peak hours |
| Keep constraints enabled in production | Disable constraints "for performance" in OLTP |

Common mistakes: expecting `CHECK (col IN ('A','B'))` to reject null; using
`UNIQUE` on a nullable column and being surprised by many nulls; dropping a
constraint to load data and forgetting to re-enable it.

## 9. Check yourself

??? question "Interview questions"
    1. **(Beginner)** Primary key versus unique constraint? *Primary key: one per table, no nulls. Unique: many per table, nulls allowed.*
    2. **(Beginner)** What does `ON DELETE CASCADE` do?
    3. **(Intermediate)** When are constraints checked? *At the end of the statement, or at commit if deferred.*
    4. **(Senior)** Why does an unindexed foreign key cause locking problems? *Deleting or changing the parent key needs a share lock on the whole child table to prevent new orphans.*
    5. **(Architect)** How do you enforce "one active cart per customer" on 19c? *A unique function-based index on `CASE WHEN status = 'ACTIVE' THEN customer_id END`.*

??? example "Exercises"
    1. Try to insert an order line with quantity 0. Which constraint fails? *`CK_ORDER_ITEMS_QTY`.*
    2. Why does order 1002 satisfy `ck_orders_total`? *800 - 80 + 0 = 720.*
    3. Write the unique index that allows only one `ACTIVE` cart per customer.
       ```sql
       CREATE UNIQUE INDEX uq_carts_one_active
           ON carts (CASE WHEN status = 'ACTIVE' THEN customer_id END);
       ```
