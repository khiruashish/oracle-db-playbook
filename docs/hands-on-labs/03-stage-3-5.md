# Labs: Stages 3 to 5

!!! danger "These labs need a database you are allowed to destroy"
    They shut down instances, delete files and restore from backup. Never run
    them on a shared system. Command output is illustrative.

## Lab 3.1 Instance tour

**Objective.** Connect every architecture term to something you can query.
**Prerequisites.** Chapters 3.1, 3.2. SYSDBA access.

**Steps**

```sql
SELECT instance_name, status, version_full FROM v$instance;
SELECT name, open_mode, log_mode, cdb FROM v$database;
SELECT con_id, name, open_mode FROM v$pdbs;
SELECT name, ROUND(bytes / 1048576) AS mb FROM v$sgainfo ORDER BY bytes DESC;
SELECT pname FROM v$process WHERE pname IS NOT NULL ORDER BY 1;
SELECT name FROM v$controlfile;
SELECT group#, member FROM v$logfile ORDER BY 1;
SELECT tablespace_name, file_name FROM dba_data_files ORDER BY 1;
SELECT name, value FROM v$diag_info WHERE name IN ('Diag Trace', 'Diag Alert');
```

Then: `SHUTDOWN IMMEDIATE`, `STARTUP NOMOUNT`, `ALTER DATABASE MOUNT`,
`ALTER DATABASE OPEN`, querying `V$INSTANCE.STATUS` at each stage.

**Expected results.** Status progresses `STARTED` → `MOUNTED` → `OPEN`. In
`NOMOUNT`, `V$CONTROLFILE` queries work from the parameter only and
`V$DATAFILE` fails with `ORA-01507: database not mounted`.

**Validation.** Draw the instance and its files with the real names from your system.

**Challenge.** Measure the redo generated by `UPDATE products SET unit_price = unit_price;` followed by `ROLLBACK`. Why is it more than the update alone?

??? success "Solution"
    Query `redo size` in `V$MYSTAT` before and after each step. The rollback
    applies undo, and applying undo changes blocks, which generates redo too.

## Lab 3.2 Backup and recover

**Objective.** Lose a data file and recover it with no data loss.
**Prerequisites.** Chapter 3.4. ARCHIVELOG mode.

**Steps**

```sql
CREATE TABLESPACE lab_ts DATAFILE SIZE 100M;
CREATE TABLE freshmart.lab_orders TABLESPACE lab_ts AS SELECT * FROM freshmart.orders;
```

```text
RMAN> BACKUP INCREMENTAL LEVEL 0 DATABASE PLUS ARCHIVELOG;
```

```sql
INSERT INTO freshmart.lab_orders SELECT * FROM freshmart.orders;   -- changes after the backup
COMMIT;
SELECT file_id, file_name FROM dba_data_files WHERE tablespace_name = 'LAB_TS';
ALTER TABLESPACE lab_ts OFFLINE IMMEDIATE;
-- Remove the file at the OS level (or asmcmd rm), then:
```

```text
RMAN> RESTORE TABLESPACE lab_ts;
RMAN> RECOVER TABLESPACE lab_ts;
RMAN> ALTER TABLESPACE lab_ts ONLINE;
```

(In a PDB, use the PDB-qualified form, for example
`RESTORE TABLESPACE freshmart:lab_ts;`, from the root.)

**Expected results.** Restore from the level 0 backup, then "media recovery
complete" after applying archived and online redo.

**Validation.** `SELECT COUNT(*) FROM freshmart.lab_orders;` returns **16**:
the 8 rows inserted *after* the backup were recovered from redo.

**Challenge.** Recover `lab_orders` to its state before the second insert,
without touching anything else.

??? success "Solution"
    Flashback Query if undo still covers it
    (`SELECT ... AS OF TIMESTAMP`), or `RECOVER TABLE ... UNTIL TIME ...
    AUXILIARY DESTINATION ... REMAP TABLE ...` from the backup.

**Clean up.** `DROP TABLESPACE lab_ts INCLUDING CONTENTS AND DATAFILES;`

## Lab 3.3 Flashback

**Objective.** Undo three kinds of mistake with the narrowest tool.
**Prerequisites.** Chapter 3.4.

| # | Mistake | Recovery | Validate |
|---|---|---|---|
| 1 | `UPDATE products SET unit_price = 0; COMMIT;` | `MERGE` from `products AS OF TIMESTAMP ...` | `SELECT SUM(unit_price) FROM products;` returns 1787 |
| 2 | `DROP TABLE reviews;` | `FLASHBACK TABLE reviews TO BEFORE DROP;` | 7 rows; indexes are back (with recycle-bin names: rename them) |
| 3 | A "bad release": create a guaranteed restore point, drop two tables with `PURGE`, then `FLASHBACK DATABASE TO RESTORE POINT ...; ALTER DATABASE OPEN RESETLOGS;` | Tables are back | Run `sql/grocery-application/verify.sql`: all `PASS` |

**Expected results.** As in the Validate column. (The 12 prices sum to
180 + 60 + 40 + 35 + 68 + 84 + 95 + 45 + 120 + 150 + 650 + 260 = 1787.)

**Challenge.** After step 2, the foreign keys of `reviews` are valid, but what
is different about the index and constraint names?

??? success "Solution"
    Indexes and constraints return with system-generated `BIN$...` names.
    Rename them: `ALTER INDEX "BIN$..." RENAME TO pk_reviews;` and
    `ALTER TABLE reviews RENAME CONSTRAINT "BIN$..." TO pk_reviews;`.

**Clean up.** `DROP RESTORE POINT ...;`

## Lab 3.4 Security

**Objective.** Apply least privilege and auditing, and prove them.
**Prerequisites.** Chapter 3.5.

**Steps**

1. Create `fm_app` and `fm_app_role` as in [FreshMart implementation](../grocery-application/03-implementation.md).
2. Connect as `fm_app` and test.
3. Create and enable a unified audit policy on `UPDATE` of `freshmart.products` for sessions other than `FM_APP`.
4. As a DBA account, change a price; query `UNIFIED_AUDIT_TRAIL`.

**Expected results**

| As `fm_app` | Result |
|---|---|
| `SELECT * FROM freshmart.products` | Rows |
| `EXEC freshmart.order_pkg.cancel_order(1007)` then `ROLLBACK` | Works |
| `UPDATE freshmart.orders SET status = 'CANCELLED'` | `ORA-01031: insufficient privileges` or `ORA-00942` |
| `SELECT salary FROM freshmart.employees` | `ORA-00942: table or view does not exist` |
| `CREATE TABLE t (x NUMBER)` | `ORA-01031` |

The audit trail shows one `UPDATE` on `PRODUCTS` by the DBA account, and none
for anything `fm_app` did.

**Challenge.** `fm_app` can execute `order_pkg`, which updates `orders`, yet
cannot update `orders` directly. Explain.

??? success "Solution"
    The package runs with **definer's rights**: inside it, the privileges of
    `FRESHMART` apply. The grant of `EXECUTE` exposes exactly the operations
    the package offers, and nothing else.

## Lab 3.5 Performance diagnosis

**Objective.** Create a performance problem and find it from the outside.
**Prerequisites.** Chapters 2.15, 3.6, 3.7. Use `orders_big` from lab 2.4. Diagnostics Pack views only if licensed (lab databases under the OTN developer licence may use them).

**Steps**

1. Session A: run a loop of 20,000 statements built with literals:

    ```sql
    DECLARE n NUMBER;
    BEGIN
        FOR i IN 1 .. 20000 LOOP
            EXECUTE IMMEDIATE 'SELECT COUNT(*) FROM orders_big WHERE order_id = ' || i INTO n;
        END LOOP;
    END;
    /
    ```

2. Session B: find it.

    ```sql
    --8<-- "sql/performance/sql_diagnosis.sql:literals"
    ```

3. Rewrite with a bind (`... WHERE order_id = :1' INTO n USING i`) and compare.

**Expected results.** Step 2 shows one `force_matching_signature` with
thousands of versions and `parse count (hard)` rising by about 20,000. With
the bind there is one cursor with 20,000 executions, and the loop is several
times faster.

**Validation.** `SELECT executions FROM v$sql WHERE sql_text LIKE 'SELECT COUNT(*) FROM orders_big WHERE order_id = :1%';` returns 20000.

**Challenge.** Without changing the code, how could you reduce the damage, and
what is the risk?

??? success "Solution"
    `ALTER SESSION SET cursor_sharing = FORCE` replaces literals with
    system-generated binds. Risks: it hides the application defect, affects
    every statement in scope, and changes how the optimizer treats literals
    (histograms, partition pruning with literals).

## Lab 4.1 Design review

**Objective.** Practice Stage 4 and 5 judgment on paper.
**Prerequisites.** Stages 4 and 5. No database needed.

**Scenario.** FreshMart will open in two more countries next year, expects 5
million customers in three years, and has just had a 3-hour outage caused by a
failed storage array. The CTO wants "a database that cannot go down" and has a
budget for one major initiative.

**Tasks**

1. Write RTO and RPO per failure class (server, storage, site, region, human error) and justify each with a business consequence.
2. Choose an architecture from [4.1](../high-availability/03-ha-dr-architecture.md) and write the ADR, including two rejected options.
3. Decide the data placement for the new countries ([5.2](../enterprise-architecture/01-global-architecture.md)).
4. Use the capacity model in [FreshMart scaling](../grocery-application/05-scaling.md) to estimate peak orders per second and storage at 5 million customers.
5. List the five largest risks and who owns each.
6. Write the one-page executive summary with the decision you need.

**Expected results.** There is no single right answer. A strong answer:
starts from the outage that actually happened (storage) and shows it is
covered; does not propose RAC or sharding without a requirement that needs
them; states costs and residual risks; and includes a DR test plan.

**Validation.** Have a colleague challenge it with the failure walk-through
questions in 4.1. Every "we would figure it out" is a gap.

??? success "A reference answer in outline"
    - Peak at 5M customers under the stated assumptions: about 25 orders per second; about 400 GB online after two years. One primary is sufficient.
    - Initiative: local SYNC standby with Fast-Start Failover plus a remote ASYNC standby, immutable backups, and twice-yearly switchover tests. This removes the storage single point of failure that caused the outage.
    - New countries: separate regional databases on the same automation (partitioned writers), driven by residency.
    - Rejected: RAC (does not address storage or site loss; no scalability need), multi-region active-active (conflict handling with no requirement).
    - Risks: untested failover, application connect strings, capacity of the standby, key management across regions, team capacity to run three regions.
